## Context

Seat images layer on `cistella/base:local`, and harness images add exactly one harness binary on top. A lane image therefore cannot sit directly on base: with no harness binary it could not serve seats. The handbook lane runs opencode seats, so the lane image layers on `cistella/opencode:local`.

Constraints: the fleet's pin contract (every fetched artifact sha256-pinned, verified at build), the refresh/validate/fixture machinery that covers each image track, and the standing rule that base stays lean — every seat in every lane pays base's size.

## Goals / Non-Goals

**Goals:**
- Handbook-lane seats produce PDF output from the shared pinned toolchain (pandoc 3.1.13 + XeTeX + DejaVu). The lane validated 3.1.3 output and re-validates against 3.1.13 at rollout.
- Every seat gets a working font stack so the maps lane's vendored-fonts workaround can be removed.
- The new image joins the refresh, validation, and fixture contract like every other track.

**Non-Goals:**
- No TeX engine or pandoc in base. No texlive-fonts-extra anywhere (~1.7 GB for glyphs the handbook never typesets). No version float beyond the 3.1 series on pandoc: both teams accept latest-3.1.x, with LitRPG re-validating handbook output at rollout since output diffs are the failure mode.

## Decisions

- **Lane variant `images/cistella/opencode-pandoc/`, `FROM localhost/cistella/opencode:local`, over base inclusion or a harness-less layer.** The document toolchain (~560 MB installed as measured; the TeX tree dominates, not pandoc's Haskell runtime) is paid only by handbook-lane seats, and the harness comes from the validated opencode layer rather than being reinstalled. Alternatives considered: base inclusion (rejected — every lane pays for one lane's pipeline); a harness-less layer on base (rejected — no harness binary, cannot serve seats); per-seat apt at container start (rejected — unpinned, slow, network-dependent per launch).
- **Capability naming (`opencode-pandoc`) over lane naming.** Harness images are named after harnesses; the first sketch (`handbook`) described a single lane and was rejected as over-fitted once a second team's deferred need made the capability shared in prospect. The chosen name is harness + capability: the opencode image plus a document toolchain. The rejected lane naming is recorded here so a future reader does not re-propose it: `handbook` (single-lane) then `opencode-litrpg-handbook` (team-and-lane) were both superseded when Conlang's anticipated need turned one team's lane into a shared capability.
- **Baked toolchain over a host mount.** Mounting the TeX distribution from the host would put lane-specific bulk on every seat host, float versions with host package updates (output diffs are the lane's stated failure mode, and the pin contract cannot cover host state), and entangle seat reproducibility with host state. Baking keeps the toolchain pinned, versioned, and confined to the seats that need it; host mounts stay limited to the existing shared-state taxonomy. A host mount suits iterating on the TeX set during development, not production seats.
- **Pandoc 3.1.13 (latest 3.1.x) as a pinned upstream tarball, not the trixie package.** Trixie ships 3.1.11.1 and the lane validated 3.1.3, but both teams accept latest-3.1.x with LitRPG re-validating at rollout. Upstream publishes both `linux-amd64` and `linux-arm64` tarballs for 3.1.13 (verified), so the standard per-arch sha256 pin applies, same shape as the uv/opencode/gh tracks. The pin is HELD (notify-only with a hold_reason naming the series policy): drift is reported on ANY newer stable upstream release -- within the 3.1 series and above it -- and never auto-bumped. This also satisfies Conlang's documented pandoc >= 3.1 future minimum, so the anticipated second consumer starts compatible.
- **Explicit ordered three-level dependency, no generalized DAG.** The lane image's immediate parent is the opencode image, whose parent is base. The contract, stated completely: (a) `build-image opencode-pandoc` builds base, then opencode, then the lane image (parents from cache in standalone mode, `--no-cache` applying to the named image only -- the existing semantic); refresh-images builds in dependency order. (b) The lane image's effective fingerprint covers the closure -- base pins + base recipe, opencode pins + opencode recipe, lane pins + lane recipe -- so an opencode-only or base-only change rebuilds the lane image even when the pandoc pin is HELD. "Held drift never triggers rebuild" means pandoc drift alone, never exemption from inherited changes. (c) Rollback and failure-restore cover the affected closure's pins and `:previous` tags, same guarantee as the existing tracks. Alternatives considered: a generalized DAG framework (rejected -- an explicit ordered third track is sufficient and matches the existing script structure, which already special-cases base-first ordering).
- **Recipe content in the fingerprint, not pins alone.** Today the refresh fingerprint hashes only pins files, so a fonts-only base Containerfile change with unchanged pins is invisible to `--apply` even when labels match. The guarantee chosen: automatic recipe-drift detection -- fingerprints cover pins AND Containerfile bytes for every track in the closure, descendants included. One-time consequence: every existing track reads stale once and converges in a single documented bootstrap rebuild round. The alternative (a manual versioned recipe stamp bumped on each Containerfile edit) was rejected as unenforceable -- stamps drift from the content they claim to version. A controlled documented initial rebuild bootstraps the new hashes; it is not advertised as anything else.
- **Reproducibility scoped to the validated built image, not to rebuilds.** `apt-get update` fetches current repository indices independently of the base image digest, so `--no-cache` refreshes rather than freezes apt state. No Debian snapshots are introduced here. The reproducibility contract is: the validated built image digest, with recorded package/font versions and parent image digests -- identical pins on a later rebuild are NOT promised identical PDFs. Byte-identical rebuilds would need snapshots or version locks, proposed deliberately if ever required.
- **Rendered-content acceptance, not just successful production.** The end-to-end scenario asserts extracted content, not exit status: `pdftotext` output must contain the em-dash and the arrow and the TOC entries, and `pdffonts` must show every font embedded (no unembedded fallback signaling a missing glyph). Installed fonts and default XeTeX selection do not prove the glyph rendered; pandoc builds the PDF in a temp dir whose transcript does not survive, so embedding (`pdffonts`) and extraction (`pdftotext`) are the observable proof, not the build log.
- **TeX via Debian trixie packages (`texlive-xetex`, `texlive-latex-recommended`, `texlive-fonts-recommended`, `texlive-latex-extra`, `lmodern`), not upstream.** TeX Live has no per-version tarball track comparable to the harness releases; the distro digest pin plus `--no-cache` rebuilds is the existing practice for all apt content. XeTeX is the engine (Unicode-native, matches the DejaVu/Latin Modern coverage the lane confirmed). The `lmodern` package is required explicitly (not assumed present): pandoc's default LaTeX template loads `lmodern.sty` itself, and the end-to-end build fails without it. Likewise `texlive-fonts-recommended` is distinct from `texlive-latex-recommended` and equally required: it carries the PostScript font metrics (including Zapf Dingbats, which hyperref's XeTeX driver loads for link handling), and the build fails at `pzdr` without it. Both findings came from the end-to-end check, which is exactly the template-drift class it exists to catch.
- **fontconfig + fonts-dejavu-core in base.** ~5 MB installed, benefits every lane, and is the precondition for removing the maps lane's vendored fonts. DejaVu Sans + Sans Mono both ship in `fonts-dejavu-core`, matching the lane's standardized set.
- **poppler-utils in the lane image, not base.** PDF utilities serve the handbook pipeline only; nothing else in the fleet names them.

## Risks / Trade-offs

- [Pinned 3.1.13 sits ahead of trixie's 3.1.11.1 but the 3.1 series is closed (upstream at 3.13)] → Accept: series stability over freshness for a batch document converter. State it plainly: the pin is pinned until an explicit both-teams decision, and drift detection notifies on ANY newer stable upstream (within and above the series) rather than tracking it — which is what makes the held pin (HOLD_VARS + hold_reason + no-bump fixtures for both within-series and above-series drift) the right shape rather than an omission. A 3.x jump would need both teams' re-validation. Compatibility is not a permanent exemption: a security-relevant advisory requires explicit re-validation/update or stopping that use. Pandoc --sandbox is not a PDF-engine sandbox; no new sandbox subsystem is requested — the lane scope stays at the existing trusted-project tooling authority, not an untrusted document service.
- [TeX packages float within the trixie digest] → Scoped, not solved: apt state is mutable, so reproducibility is the validated built image digest with recorded package/font versions and parent digests — not identical PDFs from identical pins on a later rebuild. A future trixie point release moves TeX under the same digest-update flow as everything else, and the closure fingerprint marks descendants stale.
- [Recipe-content fingerprinting makes every existing track stale once] → Accept as the one-time bootstrap cost: a single documented rebuild round converges all labels, after which recipe drift is automatic. The alternative — a fonts-only base change silently converging while the variant lacks the promised fonts — is exactly the false-convergence this change must not ship.
- [A fifth image track adds refresh/validate/fixture maintenance] → Mitigated by following the existing track shape exactly (pins.sh, drift detection, validate-image target, fixture coverage) plus the explicit ordered third-track rules above, rather than inventing lane-specific tooling or a generalized DAG.
- [Lane seats must be recreated to pick up the image] → Handbook-lane rollout only; the general fleet is untouched (base gains ~5 MB, functionally inert without consumers).

## Migration Plan

Build base (fonts only), rebuild the opencode image so the lane layer sits on the current harness, build the lane image `--no-cache`, validate (`validate-image opencode-pandoc` including the end-to-end rendered-content check, fixture suite), then recreate handbook-lane seats through the coordinator against the lane profile. The recipe-content fingerprint change makes all existing tracks stale once: converge them in the same documented bootstrap rebuild round and record the measured sizes and package/font versions with the built digests. Rollback restores the affected closure's pins and `:previous` tags (refresh-images --rollback); seat rollback is recreation against `:previous` tags; no shared state is involved.
